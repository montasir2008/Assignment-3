Warmup
------

Q1. Looking at a call stack listing in a debugger, what is the indication that the program being debugged uses recursion?
A1. If a program uses recursion, the call stack should show multiple iterations of the function being ran. The should also have slightly different parameters in each call.

Q2. Subtract the innermost level number from the outermost to get the maximum count of stack frames that fit in the capacity of the call stack. How many stack frames fit in your system's call stack?
A2. In my case, I have 43273 stack frames in my call stack before a stack overflow error was reached.

Q3. Describe how the symptoms of infinite recursion differ from the symptoms of an infinite loop.
A3. The symptoms of infinite recursion are slightly different from a loop. This is because infinite recursion causes a crash while a loop just causes a program to run forever without stopping. You also dont see a large number of stack frames for a infinite loop usually.

Q4. In place of selecting values over a defined range, an alternate approach would be to randomly select values for base and exponent. Such a test case would test something different each time you ran it. This test approach is part of a larger approach known as "fuzz" testing. What do you see as possible benefit and downside of randomness being used in a test case?
A4. The possible benefits of ramdomness is that certain edge cases may be hit in testing. You can also cover a massive number of inputs. The downsides are that one failure may be very hard to reproduce once you randomly hit it once.

Q6. Explain how the recursive structure of `recPower` results in a Big-O runtime of `O(lgN)` relative to the size of its `exp` argument.
A6. The structure of recPower resutls in O(logN) runtime because the exp rgument is halved everytime a recursive call happens. Basically, the amount of operations ran depends on how many times exp can be divided by 2. This is logarithimic.

Q8. Give a rough estimate of the maximum length sequence that could be successfully merged on your system assuming a recursive implementation of `binaryMerge`.
A8. THe maximum lenght sequence that could successfully be merged is about 43273 because that is the maximum number of stack frames the compiler allows.

Q9. What would be the observed behavior if attempting to recursively merge a sequence larger than that maximum?
A9. The observed behavior would be called stack overflow as there would be too many calls to the function happening. The program would just end as we saw before.

Q13. You run `recMultiMerge` on a sequence of size 1 million and see that it completes just fine. Explain why this is not running afoul of the call stack capacity limitation.  _Hint_: How many stack frames (levels) are expected to be on the call stack at the deepest point in the recursion in `recMultiMerge`?
A13. Even if we have a million elements ran on the sequence, the number of stack frames is going the logk where k is n in this case since we have seperate queues. The log of a million is about 20 which is practically nothing here. This is extremely far from our limit of thousands of frames.
